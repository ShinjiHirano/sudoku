# 数独 Web アプリ実装計画書

## 1. 目的

旧 `isitdx` プロジェクトの数独機能を、スマートフォンと PC のブラウザだけで動作する独立した Web アプリとして作り直す。静的ファイルだけで配信できる構成にし、GitHub Pages で公開可能にする。

あわせて、雑誌などに掲載された 9×9 数独をカメラ撮影または画像選択から取り込み、問題データとして登録できるようにする。画像の外部送信は行わず、認識・保存は原則として端末内で完結させる。

## 2. 既存実装の調査結果

調査対象は `~/docker/isitdx/app_isitdx/app/static/js/numberplace.js` および CSS である。

### 引き継ぐ機能

- 9×9 盤面と数字パレット
- プレイ／問題編集モード
- 行・列・3×3 ブロックの重複チェック
- 同じ数字と関連マスの強調表示
- 候補数字の自動計算と手動切替
- 問題集、前後の問題への移動

### 作り直す理由

- 問題集の取得・保存が認証付きバックエンド API に依存しており、静的ホスティングでは使えない。
- 権限が特定メールアドレスで固定され、編集機能を一般利用者向けに提供できない。
- `Board` が DOM 操作、ゲーム状態、候補計算、編集処理を併せ持ち、変更・テストがしづらい。
- 右クリック、ダブルクリック、500px 固定レイアウトに依存しており、スマートフォンで扱いにくい。
- 数値と文字列の混在、未使用のダブルクリック処理、例外を `alert` へ直接出す作りなどを整理する必要がある。

## 3. 方針と技術選定

| 領域 | 採用方針 | 理由 |
| --- | --- | --- |
| アプリ | TypeScript で実装し、ブラウザでは JavaScript として実行 | 状態・型を明確にしつつ、要件どおりの JavaScript Web アプリにする |
| ビルド | Vite | 軽量で GitHub Pages 向けの静的成果物を生成できる |
| UI | フレームワークに依存しない DOM/CSS（必要なら後から Web Components 化） | 数独の画面規模に対して依存を小さく保つ |
| 状態管理 | 純粋な盤面ルールモジュール + UI 用ストア | 数独ロジックを DOM から切り離し、単体テスト可能にする |
| 永続化 | IndexedDB を主、JSON のインポート／エクスポートを副 | ブラウザの一時メモリではなく、端末内に永続保存できる。ブラウザデータ削除に備えて持ち出しもできる |
| 任意クラウド保存 | Google Drive の JSON ファイルを利用者操作で開く／保存する | 静的アプリのまま端末間移行・バックアップを行える。自動同期は初版の対象外 |
| カメラ | `getUserMedia` と画像ファイル選択 | iOS/Android/PC のいずれでも入口を用意する |
| 画像処理 | ブラウザ内の画像処理ライブラリ（OpenCV.js を候補）+ 数字 OCR（Tesseract.js を候補） | 盤面の射影補正、81 マス分割、数字認識をサーバーなしで実現する |
| 配信 | GitHub Actions で `dist/` を GitHub Pages へデプロイ | 公開物とソースを分離し、再現可能にする |

OCR ライブラリは試作時にスマートフォン実機で精度・初回ダウンロード量・処理時間を測定して最終決定する。ライブラリを CDN から実行時取得せず、ビルド成果物に固定バージョンで含めることを原則とする。

Google Drive 連携には Google Identity Services、Google Picker、Google Drive API を用いる。アプリが作成した、または利用者が Picker で開いたファイルだけを扱える `drive.file` 権限を使い、Drive 全体の読み書き権限は要求しない。GitHub Pages だけで運用する間は短期アクセストークンを利用者操作の都度取得し、ブラウザにリフレッシュトークンを保存しない。そのため、バックグラウンド自動同期は対象外とする。

## 4. 全体構成

```text
ブラウザ
├─ UI
│  ├─ プレイ画面 / 編集画面
│  ├─ 問題集管理
│  └─ 画像取込・確認画面
├─ アプリケーション層
│  ├─ 盤面・入力・履歴の状態管理
│  └─ 保存データの入出力
├─ ドメイン層
│  ├─ 数独ルール、候補、検証、解の個数判定
│  └─ 問題データの形式・変換
├─ 端末内データ
│  └─ IndexedDB（問題集、プレイ状態、設定）
└─ 画像取込（端末内処理）
   ├─ 撮影／画像選択 → 盤面領域指定 → 射影補正
   ├─ 81 マス分割 → 数字認識 → 検証・手修正
   └─ 問題として保存
```

## 5. 段階的な実装計画

### フェーズ 0: 土台と移行設計

1. Vite + TypeScript の静的アプリを作成する。
2. 旧形式（9 行×カンマ区切り）を読み込める JSON 変換機能を用意する。
3. ESLint、Prettier、Vitest、GitHub Actions の基盤を整える。

完了条件: ローカルでビルド・テストでき、GitHub Pages 用の成果物を生成できる。

### フェーズ 1: 数独プレイの MVP

1. レスポンシブな 9×9 盤面、数字キーパッド、キーボード操作を実装する。
2. 問題編集、入力削除、候補メモ、重複表示、同数・関連マスの強調を実装する。
3. Undo/Redo、クリア、完成判定を実装する。
4. IndexedDB への自動保存と問題集の JSON 入出力を実装する。

完了条件: 旧版のプレイ・編集・候補機能をスマートフォンでも問題なく利用でき、ページ再読み込み後も復元される。

### フェーズ 1.5: 持ち出し・Google Drive 保存

1. 全問題集または指定問題集を JSON ファイルとして端末へエクスポートできるようにする。
2. JSON ファイルを検証してインポートできるようにする。
3. Google Cloud の OAuth クライアントを設定し、Google Drive に JSON を新規保存・上書き保存できるようにする。
4. Google Picker で利用者が選んだ JSON だけを読み込み、インポートできるようにする（保存機能の安定後に追加）。

完了条件: Google にログインしていない利用者もファイルの入出力を利用でき、連携を許可した利用者だけが、明示操作で指定した Drive ファイルを開く・保存できる。

### フェーズ 2: カメラ取込 MVP

1. カメラ撮影と画像選択を実装する。
2. 画像上で四隅を利用者が指定できる盤面切り出し UI を実装する。
3. 射影補正後の盤面を 81 マスに分割し、数字 OCR を実行する。
4. 認識結果のマスごとの修正画面を実装し、検証済みの問題だけを保存できるようにする。

完了条件: 典型的な印刷問題を撮影し、利用者が確認・修正して問題集に登録できる。自動認識が不確かな場合も誤ったまま保存されない。

### フェーズ 3: 品質・公開

1. 実機（iOS Safari、Android Chrome、PC Chrome/Firefox/Safari）で検証する。
2. OCR の精度、処理時間、失敗画像を記録し、前処理を調整する。
3. アクセシビリティ、オフライン利用、初回起動時のサイズを改善する。
4. GitHub Pages 公開、利用方法とプライバシーの文書化を行う。

## 6. 主要なリスクと対策

| リスク | 対策 |
| --- | --- |
| 写真の傾き、影、罫線、誌面レイアウトで OCR が誤る | 自動検出だけに依存せず、四隅調整と 81 マス確認を必須にする |
| OCR の初回読み込みが重い | 画像取込画面を開いた時点で遅延読み込みし、プレイ画面は軽く保つ |
| スマホのカメラ権限・ブラウザ差異 | カメラ失敗時にも画像ファイル選択を必ず提供し、HTTPS の GitHub Pages で配信する |
| ブラウザの保存領域が消える | JSON エクスポートを提供し、重要な問題は利用者がバックアップできるようにする |
| Google Drive の認可情報を静的サイトに長期保存してしまう | リフレッシュトークンは保存せず、利用者操作の際だけ短期トークンを取得する。連携は選択機能とし、通常の JSON 入出力を常に提供する |
| 雑誌画像の著作権・プライバシー | 画像は外部送信しない。取り込んだ画像は既定では保存せず、数独の数値データだけを保存する |
| 問題に解がない／複数解がある | 登録前に矛盾・解の個数を検査し、警告の上で保存可否を利用者に示す |

## 7. 成果物

- 静的 Web アプリのソースコード
- GitHub Pages へのデプロイ設定
- 単体テスト・主要操作の E2E テスト
- 本仕様書、利用方法、JSON データ形式の説明
- 旧 `isitdx` 形式からの移行手順

## 8. 今回の決定範囲

初版ではログイン、サーバー同期、他人との共有、問題の自動生成は対象外とする。これらは GitHub Pages の静的配信と端末内処理という前提を崩すため、必要になった時点で別フェーズとして検討する。

Google Drive は利用者が明示操作するファイル保存・読込のみを初版対象に含める。自動バックアップ、複数端末間の競合解決、共有フォルダ・共同編集はサーバー側の安全な認可情報と同期設計を要するため対象外とする。
